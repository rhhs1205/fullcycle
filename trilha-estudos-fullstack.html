02

Primeiros conceitos

Antes de instalar qualquer coisa, vale entender o que cada palavra significa. Volte a este capítulo sempre que se perder.

Código, arquivo e projeto

Código é texto com instruções para o computador, escrito numa linguagem de programação. Neste guia a linguagem principal é o TypeScript, uma versão do JavaScript que avisa erros antes de rodar.

O código fica em arquivos comuns, como um documento de texto, só que com outra extensão: .ts para TypeScript, .html para estrutura de páginas, .css para aparência, .json para configurações.

Um projeto é uma pasta com todos os arquivos de um sistema. É nessa pasta que você e o Claude vão trabalhar.

O terminal

O terminal é uma janela onde você conversa com o computador escrevendo comandos em vez de clicar. Parece antigo, mas é o jeito mais rápido e preciso de instalar ferramentas e rodar projetos. Você digita um comando, aperta Enter e o computador responde com texto.

Analogia

Clicar em ícones é como apontar para fotos no cardápio. O terminal é como falar o pedido exato para o garçom: dá mais trabalho no começo, mas não tem ambiguidade.

A IA erra. Ela escreve com confiança mesmo quando está errada. Você é responsável por tudo que vai para o projeto. Por isso este guia ensina as peças do sistema: para você conseguir conferir o que o Claude fez.

03

O mapa do sistema

Quase todo sistema web tem três camadas, e cada uma só conversa com a vizinha. A analogia que vamos usar no guia inteiro é a de um restaurante.

No restauranteNo sistemaResponsabilidade
ClienteNavegadorQuem usa. Só vê o cardápio e recebe o prato.
Salão e garçomFrontend AngularMostra as telas, anota o pedido, leva para a cozinha e serve a resposta.
CozinhaBackend NestJSConfere o pedido, segue a receita (regras de negócio), protege o acesso.
DespensaPostgreSQL em containerGuarda os dados de forma organizada e permanente.
Por que isso importa

O cliente nunca entra na cozinha. Por isso senhas, regras importantes e acesso ao banco ficam no backend — nunca no frontend, que roda no computador do usuário e pode ser inspecionado por qualquer um.

Onde o Claude Code entra

Resumo do capítulo

Um sistema web tem três camadas: o frontend (Angular) mostra as telas, o backend (NestJS) aplica as regras e o banco (PostgreSQL) guarda os dados. Cada uma só conversa com a vizinha. O Claude Code trabalha na pasta do projeto, que contém as três.

sudo snap install code --classic

Node roda o Angular e o NestJS. Use sempre a versão LTS (suporte longo). Instale pelo nvm, que troca de versão sem sudo e sem brigar com o Node do sistema.

O terminal só "enxerga" programas novos quando é reaberto. Se aparecer command not found logo depois de instalar, esse é quase sempre o motivo.

6.2 Como funciona o pagamento por uso

No Console você paga pelo quanto o Claude lê e escreve, medido em tokens (pedaços de palavras). É como um celular pré-pago: você coloca créditos e eles vão sendo descontados conforme o uso. Sem uso, sem cobrança.

  • Ler um projeto grande, conversas longas e pedidos complexos gastam mais.
  • Perguntas curtas e sessões focadas em uma tarefa gastam menos.
  • Dentro do Claude Code, o comando /usage mostra quanto a sessão já custou.

  1. Peça o acesso ao seu líderEle (ou o administrador) envia um convite para o seu e-mail.
  2. Aceite o conviteAbra o e-mail e siga o link para criar a senha ou entrar.
  3. Faça login no Claude CodeComo explicado em 7.3 (terminal) ou 8.2 (VS Code), escolhendo o tipo de conta que a empresa indicou.

6.4 Caminho B: sua conta no Claude Console

  1. Crie a contaAcesse platform.claude.com e cadastre-se com seu e-mail.
  2. Adicione créditosNas configurações da conta, abra a área de cobrança (Billing), cadastre a forma de pagamento você mesmo e compre um valor pequeno para começar.
  3. Defina um limite de gastoNas configurações de limites, coloque um teto mensal. Assim um esquecimento não vira surpresa na fatura.

7.5 Ensinando o projeto ao Claude: /init e CLAUDE.md

Logo na primeira sessão de um projeto, rode:

/init

O Claude lê o projeto e cria um arquivo CLAUDE.md na raiz: um resumo da stack, dos comandos e das convenções. Esse arquivo é lido automaticamente em toda sessão naquela pasta. Revise, ajuste e faça commit dele — ele é do time.

# CLAUDE.md (exemplo)
## Stack
- frontend/: Angular + Angular Material, componentes standalone, estado com signals
- api/: NestJS + TypeORM, um módulo por assunto (categorias, tarefas, dashboard, health)
- banco: PostgreSQL 16 via docker compose, porta 5433 na máquina

## Comandos
- Tudo de uma vez: npm run dev
- Subir banco: docker compose up -d
- API: cd api && npm run start:dev   (testes: npm test)
- Front: cd frontend && npm start    (testes: npm test)

## Regras
- Todo endpoint novo tem teste unitário no service.
- Nunca commitar o arquivo .env.

Modos de permissão

O modo decide se o Claude pede autorização antes de agir. Nas versões atuais a sessão começa em Auto (age sozinho, com um verificador de segurança). Enquanto aprende, use Manual, que pergunta antes de cada mudança:

claude --permission-mode manual
  • Manual — pergunta antes de editar arquivos e de rodar comandos. Use este agora.
  • Plan — só lê e propõe um plano; não altera nada. Ótimo para começar uma tarefa.
  • Auto — age sem perguntar na maioria das vezes. Para quando você já tiver experiência.

Shift+Tab troca de modo durante a sessão. Para deixar o Manual como padrão em todas as sessões, veja a seção 8.5.

// tarefas.service.ts — quem fala com a API
@Injectable({ providedIn: 'root' })
export class TarefasService {
  private http = inject(HttpClient);
  private api = 'http://localhost:3000/tarefas';

  listar()              { return this.http.get<Tarefa[]>(this.api); }
  criar(titulo: string) { return this.http.post<Tarefa>(this.api, { titulo }); }
}
// tarefas.component.ts — a tela
@Component({
  selector: 'app-tarefas',
  template: `
    <input #campo placeholder="Nova tarefa" />
    <button (click)="adicionar(campo.value)">Adicionar</button>   <!-- evento -->
    <ul>
      @for (t of tarefas(); track t.id) {                        <!-- repete -->
        <li>{{ t.titulo }}</li>                                 <!-- mostra -->
      } @empty {
        <li>Nenhuma tarefa ainda.</li>
      }
    </ul>
  `,
})
export class TarefasComponent {
  private service = inject(TarefasService);
  tarefas = signal<Tarefa[]>([]);                              // estado vivo

  constructor() {
    this.service.listar().subscribe(lista => this.tarefas.set(lista));
  }

  adicionar(titulo: string) {
    this.service.criar(titulo)
      .subscribe(nova => this.tarefas.update(l => [...l, nova]));
  }
}

// criar-tarefa.dto.ts — o que a API aceita
export class CriarTarefaDto {
  @IsString()
  @IsNotEmpty()
  @MaxLength(120)
  titulo: string;
}

// tarefas.controller.ts — as rotas
@Controller('tarefas')
export class TarefasController {
  constructor(private readonly service: TarefasService) {}

  @Get()
  listar() { return this.service.listar(); }

  @Post()
  criar(@Body() dto: CriarTarefaDto) { return this.service.criar(dto); }
}

// tarefas.service.ts — a regra
@Injectable()
export class TarefasService {
  constructor(@InjectRepository(Tarefa) private repo: Repository<Tarefa>) {}

  listar() { return this.repo.find({ order: { concluida: 'ASC' } }); }
  criar(dto: CriarTarefaDto) { return this.repo.save({ ...dto, concluida: false }); }
}

Banco de dados em container

A despensa, dentro de uma caixa. O PostgreSQL guarda os dados. Em vez de instalar o banco na máquina, rodamos ele dentro de um container Docker: todo mundo do time usa a mesma versão, sobe com um comando e apaga sem deixar sujeira.

Imagem, container e volume

O arquivo docker-compose.yml

services:
  db:
    image: postgres:16                  # a forma
    container_name: estudo-db           # o nome do bolo
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
      POSTGRES_DB: tarefas
    ports:
      - "5433:5432"                     # porta da máquina : porta do container
    volumes:
      - dados:/var/lib/postgresql/data  # o pote
    healthcheck:                        # avisa quando o banco está pronto para conexões
      test: ["CMD-SHELL", "pg_isready -U app -d tarefas"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  dados:
Por que 5433 e não 5432?

Dentro do container o PostgreSQL continua na porta padrão, 5432. Do lado da sua máquina usamos a 5433, porque é comum já existir outro PostgreSQL ocupando a 5432 (de outro projeto, por exemplo), e dois programas não podem usar a mesma porta. Se a 5432 estiver livre e você preferir, troque nos dois lugares: ports no docker-compose.yml e DATABASE_URL no api/.env.

O caderno de receitas da cozinha. No capítulo 9 você aprendeu a escrever um bom pedido. Uma skill é um bom pedido salvo numa pasta, com nome e descrição, versionado junto com o projeto. O Claude consulta a receita certa sozinho quando o assunto aparece — ou você chama pelo nome, como /criar-endpoint.

Como o Claude lê uma skill: três níveis

Estrutura de pastas

fullcycle/
└── .claude/
    └── skills/
        └── criar-endpoint/       # o nome da pasta vira o comando /criar-endpoint
            ├── SKILL.md          # obrigatório
            ├── padroes.md        # opcional — nível 3
            └── scripts/          # opcional — nível 3

Skills em .claude/skills/ são do projeto e vão para o Git: o time inteiro usa. Skills em ~/.claude/skills/ são pessoais e valem em todos os seus projetos.

Anatomia do SKILL.md

---
name: criar-endpoint                         # minúsculas, números e hífens
description: Cria um endpoint REST no NestJS deste projeto
  seguindo o padrão module/controller/service/DTO. Use quando
  pedirem nova rota, recurso, CRUD ou endpoint na API.       # O QUE faz + QUANDO usar
---

# Criar endpoint NestJS

1. Rode `nest g resource <nome>` dentro de `api/`.
2. Todo DTO de entrada usa class-validator.
3. Regra de negócio fica no service; o controller só repassa.
4. Crie ou atualize o teste unitário do service.
5. Rode `npm test` e mostre o resultado antes de finalizar.

Para nomes de rotas e formato de erros, leia padroes.md.    # aponta para o nível 3

SDD com Spec Kit

A planta antes da obra. Spec-Driven Development é escrever primeiro o que precisa ser feito e por quê, depois como, depois quebrar em tarefas pequenas — e só então a IA programa. A especificação vira a fonte da verdade: se o requisito muda, muda a spec primeiro.

Instalando e iniciando

uv tool install specify-cli --from git+https://github.com/github/spec-kit.git
specify init projeto-estudo --ai claude     # projeto novo
# ou, num projeto que já existe:
cd fullcycle && specify init --here --ai claude

claude                                      # os comandos /speckit.* ficam disponíveis
Confira o README antes

O Spec Kit evolui rápido e as flags podem mudar entre versões. Os comandos acima seguem o README do repositório github/spec-kit.

/speckit.specify → spec.md

# Lista de tarefas pessoais
## Histórias
- Como usuário, vejo minhas tarefas ao abrir a página.
- Como usuário, crio uma tarefa informando o título.
- Como usuário, marco e desmarco uma tarefa como concluída.
## Regras
- Título obrigatório, até 120 caracteres.
- Concluídas aparecem riscadas e no fim da lista.
- Se a API estiver fora, aparece "Tente de novo em instantes".
## Fora do escopo
- Login, várias listas, datas de vencimento.

Você revisa: não tem tecnologia aqui? Toda regra é testável? Tem "fora do escopo"? Ele evita que a IA invente funcionalidade.

/speckit.plan → plan.md

- Front: Angular, componentes standalone, estado em signals.
- Back: NestJS + TypeORM, ValidationPipe global.
- Banco: PostgreSQL 16 via docker compose.
- API: GET /tarefas · POST /tarefas · PATCH /tarefas/:id

Você revisa: cada regra da spec tem onde morar? Algo desrespeita a constitution?

/speckit.tasks → tasks.md

- [ ] T001 Criar docker-compose.yml com Postgres 16
- [ ] T002 Criar entidade Tarefa (id, titulo, concluida)
- [ ] T003 Teste do TarefasService.criar (falha primeiro)
- [ ] T004 Implementar GET e POST /tarefas
- [ ] T005 [P] Implementar PATCH /tarefas/:id
- [ ] T006 [P] TarefasService no Angular
- [ ] T007 Componente de lista com estados vazio e erro

Você revisa: cada tarefa é pequena o bastante para entender o diff? [P] marca tarefas que podem ser feitas em paralelo.

/speckit.implement → código

O Claude executa as tarefas em ordem. Seu papel em cada uma: ler o diff, rodar os testes, testar na mão o que a spec promete. Se algo não bater, corrija a spec ou o código — nunca deixe os dois divergirem.

Mão na massa: as tasks do projeto

Agora é com você. Você preparou a máquina, entendeu as três camadas do sistema e viu como skills e SDD guiam o Claude. Este capítulo junta tudo num roteiro prático: abrir o projeto no VS Code, conversar com o Claude Code no painel e resolver as 5 tasks do projeto com a skill /sdd.

18.1 O que você vai fazer

O projeto tem 5 problemas colocados de propósito, descritos em tasks/index.html (abra o arquivo no navegador). Cada task traz o sintoma e uma dica, mas não a solução: descobrir onde está o problema faz parte do exercício. Para cada task você vai:

  1. Reproduzir o problema com o sistema rodando.
  2. Escrever com o Claude a spec, o plan e as tasks do SDD, revisando cada arquivo.
  3. Criar um teste que falha por causa do problema.
  4. Corrigir, ver o teste passar e rodar todos os testes.
  5. Abrir um pull request com a correção, como no capítulo 10.

Os testes que já existem passam: nenhum deles pega esses 5 problemas. Escrever o teste que pega é parte de cada task.

TaskProblemaOnde apareceNível
1Tarefa excluída continua na listaFrontendFácil
2"Criada em" mostra a hora erradaFrontendFácil
3Editar uma tarefa concluída faz ela voltar a pendenteFrontendMédio
4Nome de categoria comprido derruba a APIFrontend e APIMédio
5"Pendentes por prioridade" conta tarefas concluídasAPIMédio

Comece pelas fáceis: elas ajudam a pegar o ritmo do ciclo spec, plan, tasks e implementação antes das que atravessam mais de uma camada.

18.2 Abrindo o projeto no VS Code com o Claude Code

Faça uma vez, nesta ordem. Os detalhes de cada passo estão no capítulo 8.

  1. Suba o sistemaNum terminal, na pasta fullcycle: npm run setup (só na primeira vez) e depois npm run dev. Deixe esse terminal aberto e confira que http://localhost:4200 abre.
  2. Abra a pasta no VS CodeEm outro terminal, na mesma pasta, rode code ., ou use File → Open Folder e escolha fullcycle. Abra sempre a raiz, e não api/ ou frontend/: é na raiz que ficam a skill, as tasks e o README.
  3. Instale a extensão, se ainda não tiverAba de extensões → busque Claude Code → confira que o autor é Anthropic → Install.
  4. Abra o painel do ClaudeAbra qualquer arquivo, como o README.md, e clique na faísca (✳) no canto superior direito do editor. Na primeira vez, faça login com a conta do capítulo 6.
  5. Confira o modo ManualEmbaixo da caixa de pedido aparece o modo de permissão. Deixe em Manual (seção 8.5): assim o Claude pede autorização antes de editar arquivos e de rodar comandos, e você vê cada passo.
  6. Confira a skillDigite /skills na caixa de pedido. A skill sdd deve aparecer na lista. Se não aparecer, abra uma sessão nova: skills são descobertas quando a sessão começa.
  7. Faça uma pergunta de aquecimento@README.md me explica em 5 linhas como este projeto está organizado. Se a resposta falar de frontend, API e banco, está tudo pronto.

18.4 Resolvendo uma task, passo a passo

  1. Crie a branchUma por task, como no capítulo 10: git checkout main && git pull e depois git checkout -b fix/task-1.
  2. Peça/sdd task 1. O Claude lê a task em tasks/index.html e a constituição, e tenta reproduzir o problema.
  3. Revise a specEle cria specs/001-.../spec.md e para. Leia: está do ponto de vista de quem usa? Toda regra dá para testar? Tem "fora do escopo"? Peça ajustes ou responda pode seguir.
  4. Revise o planNo plan.md, cada regra da spec precisa ter um lugar no código e um teste. Se a mudança parecer grande demais, peça um caminho menor.
  5. Revise as tasksNo tasks.md, a primeira tarefa é sempre o teste que reproduz o problema.
  6. Acompanhe a implementaçãoEm cada tarefa, o Claude mostra o teste falhando, faz a correção e mostra o teste passando. No modo Manual, você aprova cada edição pelo diff do painel: leia antes de aceitar.
  7. Confira você mesmoRode npm test e npm run test:e2e no terminal e repita na tela o passo a passo da task. O problema sumiu?
  8. Abra o pull requestgit add ., git commit -m "fix: ...", git push -u origin fix/task-1 e gh pr create --fill. No texto do PR, conte o que o Claude fez e o que você conferiu.
Não pule as revisões

A skill para depois de cada etapa de propósito. Se você só responder "ok" sem ler, perde a parte mais importante do exercício: aprender a conferir o que a IA faz.

Resumo do capítulo

Suba o sistema com npm run dev, abra a raiz do projeto no VS Code, clique na faísca e confira /skills. Para cada task de tasks/index.html, crie uma branch, rode /sdd task N e revise spec, plan e tasks antes de deixar o Claude implementar. No fim, rode os testes e abra um pull request.
